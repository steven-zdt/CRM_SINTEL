# 3. Hallazgo P0-01 — Drift de versión de Django

## Evidencia

`requirements.txt` actualmente establece:

```text
Django>=5.0,<5.1
```

Sin embargo, la documentación oficial actual mantiene Django 5.2 como serie LTS y publica sus correspondientes releases de seguridad y mantenimiento.

Django 5.2 es LTS y tiene soporte de seguridad prolongado.

## Problema

El proyecto tiene documentación, comentarios y decisiones arquitectónicas que hacen referencia a Django 5.2, pero el archivo efectivo de dependencias todavía bloquea el proyecto en Django 5.0.x.

Esto crea:

```text
DOCUMENTACIÓN
      ↓
Django 5.2

CÓDIGO / REQUIREMENTS
      ↓
Django 5.0.x
```

Es un problema de Single Source of Truth.

## Recomendación

Definir explícitamente una política:

```text
Python 3.12
Django 5.2.x
django-tenants compatible con Django 5.2
DRF compatible
```

Y migrar:

```text
Django>=5.2,<5.3
```

preferiblemente a una versión exacta/pinned mediante lockfile.

No recomiendo mantener `>=` para el framework principal.

# 4. Hallazgo P0-02 — CI no es realmente un Quality Gate

Actualmente:

```yaml
- name: Ruff
  continue-on-error: true

- name: Bandit
  continue-on-error: true

- name: pip-audit
  continue-on-error: true
```

Esto significa que el pipeline puede terminar correctamente aunque:

```text
Ruff       ❌
Bandit     ❌
pip-audit  ❌
```

## Impacto

El workflow se llama:

```text
Pytest + Django Check + Ruff + Bandit
```

pero solamente algunas partes son realmente bloqueantes.

## Recomendación

Migrar progresivamente a:

```text
Fase 1
pytest                 BLOCKING
django check           BLOCKING
migration check        BLOCKING

Fase 2
ruff                   BLOCKING
bandit                 BLOCKING

Fase 3
pip-audit               BLOCKING
dependency review       BLOCKING

Fase 4
architecture tests      BLOCKING
multitenant isolation   BLOCKING
security regression     BLOCKING
```

La excepción temporal puede mantenerse únicamente mientras se limpia el backlog inicial.

Después:

```yaml
continue-on-error: false
```

o simplemente eliminar la propiedad.

# 5. Hallazgo P0-03 — GitHub Actions sin pinning SHA

Actualmente aparecen referencias como:

```yaml
actions/checkout@v4
actions/setup-python@v5
actions/upload-artifact@v4
```

GitHub recomienda fijar Actions a un SHA completo para obtener una referencia inmutable y reducir riesgo de supply-chain.

## Recomendación

En lugar de:

```yaml
uses: actions/checkout@v4
```

usar:

```yaml
uses: actions/checkout@<FULL_COMMIT_SHA>
```

y establecer una política de repository:

```text
Require actions to be pinned to full-length commit SHA
```

GitHub soporta explícitamente esta política.

# 7. Hallazgo P0-05 — Proxy / Host Header

La configuración contiene:

```python
USE_X_FORWARDED_HOST = True
SECURE_PROXY_SSL_HEADER = (
    "HTTP_X_FORWARDED_PROTO",
    "https",
)
```

Esto puede ser correcto detrás de Cloudflare/Nginx/Traefik, pero solamente si el proxy elimina o sobrescribe correctamente los headers externos.

## Riesgo

Si una aplicación acepta directamente:

```text
X-Forwarded-Host
X-Forwarded-Proto
```

desde clientes no confiables, se puede romper la confianza en:

```text
request.get_host()
build_absolute_uri()
CSRF
tenant resolution
redirects
URLs generadas
```

## Recomendación

Definir formalmente:

```text
Internet
   ↓
Cloudflare
   ↓
Tunnel / Proxy
   ↓
Nginx / ingress
   ↓
Django
```

y garantizar:

```text
Cliente NO controla X-Forwarded-Host
Cliente NO controla X-Forwarded-Proto
Proxy sobrescribe ambos
```

Además crear pruebas de regresión.

# 11. Hallazgo P0-09 — PostgreSQL search_path debe tratarse como frontera de seguridad

PostgreSQL advierte que el `search_path` determina qué objetos son visibles y que esquemas donde usuarios no confiables tengan capacidad de creación pueden permitir shadowing de objetos.

Esto es especialmente importante en un SaaS:

```text
public
tenant_a
tenant_b
tenant_c
```

La arquitectura debe impedir cualquier posibilidad de que un tenant controle objetos de otro schema.

## Recomendación

Auditar:

```text
search_path
database role
CREATE privilege
schema ownership
USAGE privilege
tenant creation
SECURITY DEFINER
raw SQL
database functions
```

y establecer tests de:

```text
tenant A → nunca puede leer tenant B
tenant A → nunca puede insertar en tenant B
tenant A → nunca puede modificar public
tenant A → nunca puede modificar otro schema
```

PostgreSQL proporciona además Row Level Security como mecanismo complementario cuando sea apropiado.

# 43. Conclusión técnica

CRM_SINTEL ya tiene una base arquitectónica sólida para evolucionar hacia un ERP/CRM SaaS multitenant con capacidades de IA.

El siguiente paso no debería ser añadir más módulos indiscriminadamente.

Debe ser:

```text
ESTABILIZAR
    ↓
ENDURECER
    ↓
NORMALIZAR
    ↓
AUTOMATIZAR TESTS
    ↓
CONVERTIR CI EN GATE
    ↓
CONSOLIDAR SERVICE LAYER
    ↓
CONSOLIDAR AI PROVIDER REGISTRY
    ↓
PRODUCTION HARDENING
```

La prioridad técnica más importante es eliminar la diferencia entre:

```text
"la arquitectura dice que esto está protegido"
```

y:

```text
"el código + test + CI demuestran que está protegido".
```

La documentación oficial de Django enfatiza precisamente que la seguridad debe abordarse de forma multicapa y que las configuraciones de producción deben revisarse explícitamente.

Para PostgreSQL, la revisión de `search_path`, privilegios y aislamiento de schemas debe ser considerada una frontera de seguridad real en este SaaS multitenant.

Para GitHub Actions, el siguiente endurecimiento debe incluir permisos mínimos y pinning de Actions a SHA completo.

OWASP ASVS 5.0 puede utilizarse como matriz adicional de verificación para convertir estos controles en requisitos verificables de seguridad.
