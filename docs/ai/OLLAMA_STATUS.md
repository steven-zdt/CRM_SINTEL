## Incidente real durante Fase 1/2 (2026-09-24) -- causa raíz y fix

**Qué pasó:** al correr la primera inferencia real con `qwen3.5:9b` (6.6GB) CPU-only, sin ningún límite de recursos en el contenedor `ollama`, el proceso saturó la VM de WSL2 completa (CPU y RAM al 100%) y **ahogó al propio motor de Docker Desktop** -- `docker ps`/`docker compose ps` devolvían `500 Internal Server Error` en TODOS los contenedores, no solo Ollama (el stack completo del usuario -- web/db/redis/celery/etc. -- quedó inalcanzable). Ni siquiera `docker kill` respondía (se colgó esperando la misma API rota). Requirió que el usuario liberara recursos manualmente y reiniciara Docker Desktop por completo para recuperar el motor.

**Causa raíz real (dos capas, no una):**
1. **Sin límite de recursos en el contenedor `ollama`** -- nada impedía que un solo contenedor consumiera toda la VM.
2. **La VM de WSL2 solo tenía 3.8GB de RAM asignados** (`%UserProfile%\.wslconfig`, `memory=4GB` -- fijado en una sesión anterior, F33.15-B/2026-08-16, específicamente para evitar OTRO problema de colapso de Docker Desktop con el límite dinámico de 50% RAM). Un modelo de 6.6GB no cabe ahí bajo ninguna circunstancia.

**Fix aplicado (con aprobación explícita del usuario en cada paso, host real: 12GB físicos):**
- `docker-compose.yaml::ollama` -- `mem_limit: 3g`, `cpus: 4` (verificado con `docker inspect`: `3221225472` bytes / `4000000000` nanocpus). Protege al resto del stack sin importar qué pase dentro del contenedor de Ollama.
- `.wslconfig` -- `memory` subido de `4GB` a `7GB` (deja ~5GB para Windows + apps del usuario). Riesgo conocido y documentado inline en el propio archivo: el límite dinámico original (5.9GB) ya había causado colapsos con Chrome/Edge/Claude/Antigravity IDE abiertos -- si se repite, el primer paso es bajar este número de nuevo antes de tocar nada más.
- **Modelo cambiado de `9b` a `4b`** (3.4GB) -- pedido explícito del usuario tras el incidente, further reduce el riesgo.

**Verificado tras el fix:** segunda corrida de inferencia real, los 9 servicios del stack se mantuvieron `healthy` durante toda la ejecución (5m26s). Sin repetición del incidente.
