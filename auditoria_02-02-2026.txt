1.2 Discrepancia BLOQUEANTE — primary_domain no existe en serializer

// tenants_manager.js

3. Capacidad para ≥20 Tenants
3.1 ✅ Aprovisionamiento automatizado disponible
Existe apps/public/tenants/management/commands/generar_tenants_prueba.py que crea hasta 100 tenants con datos realistas (empresa, clientes, cotizaciones, proyectos). Uso:


python manage.py generar_tenants_prueba --cantidad 100 --con-datos
Además apps/public/tenants/factories.py usa factory.Sequence (ilimitado), y existen tests de aislamiento en tests/multitenant/.

Veredicto: la implementación soporta ≥20 tenants funcionalmente.

3.2 ❌ Sin pruebas de carga reales
No hay benchmark de tiempo de respuesta con 20/50/100 tenants poblados.
No hay métricas de duración de migraciones por-tenant.
Sin medición de footprint de conexiones PostgreSQL bajo concurrencia.
3.3 🔴 Riesgos de escala detectados (verificados)
N+1 / snapshot completo en cada GET de listado de tenants — apps/public/tenants/api/viewsets.py:62-64:


def get_queryset(self):
    snapshot = list(Client.objects.values("id", "schema_name", "nombre"))
    logger.info(... clients=%s, snapshot)  # imprime TODOS los tenants en cada request
Con 100 tenants, esto carga 100 filas + las loguea en INFO en cada listado. En prod inflará logs y tiempo.

prefetch_related("domains") siempre activo (viewsets.py:45) — se prefetchan dominios incluso para list endpoints donde no se rendean detalles.

3.4 Cuotas / planes — ❌ ausentes
No hay TENANT_QUOTA_LIMIT, MAX_TENANTS_PER_PLAN, ni validación de paid_until/on_trial antes de crear tenants. Cualquier admin puede crear infinitos.
