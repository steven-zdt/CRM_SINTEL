0. TL;DR — Veredicto Directo
El stack actual (Tabulator + vanilla JS modular + HTMX + Bootstrap) es razonable para un SaaS contable, pero NO es la causa de tus problemas con el CRUD. La causa real es un bug arquitectónico verificado (cliente HTTP roto en módulos tenant), inconsistencias entre lo documentado y lo implementado, y duplicación de plantillas. NO recomiendo migrar a React/Vue ahora. Recomiendo consolidar y arreglar primero (3-4 semanas) y, en 6-12 meses si crece la base de tenants, evaluar HTMX + Alpine.js (mínima fricción, máximo retorno).

1. 🐛 LA CAUSA REAL DE TUS PROBLEMAS DE CRUD (VERIFICADO)
He confirmado directamente leyendo el código:

🔴 BUG CRÍTICO — clientesAPI nunca se inicializa en módulos tenant
Evidencia 1 — http.js:106-159:


const http = { async get(...){}, async post(...){}, async patch(...){}, ... };
window.http = http;   // ← se exporta como OBJETO con métodos
Evidencia 2 — clientes.api.js:17-20:


if (typeof w.http !== 'function') {
    console.error('[clientes.api] http() no está disponible.');
    return;   // ← EARLY EXIT: clientesAPI jamás se define
}
typeof {} === 'object', no 'function'. Por tanto, la guarda siempre dispara return y w.clientesAPI nunca queda definido.

Evidencia 3 — http.js solo se carga en console/base.html, NO en apps/tenant/core/templates/tenant/base.html. Es decir, en cualquier vista de tenant, window.http literalmente no existe.

Evidencia 4 — Llamadas como w.http('GET', url) (clientes.api.js:31) asumen una firma (method, url, payload) que nunca existió en http.js (cuyo objeto solo tiene .get(url, params), .post(url, data), etc.).

Consecuencia: todos los CRUD de Clientes (y muy probablemente Contabilidad/Inventario/Proveedores que repiten el mismo patrón) fallan en silencio: el botón Guardar dispara w.clientesAPI.update(...) → TypeError: Cannot read property 'update' of undefined → handler captura el error sin renderizar feedback al usuario.

Esto es exactamente lo que tú estás viviendo.

🔴 BUG CRÍTICO 2 — Estructura de respuesta divergente
http.js:90-94 retorna el data directo (o lanza Error). Pero los editores hacen:


if (response && response.ok) { ... }   // ← response.ok no existe en data plano
else { errorData = response.data; ... } // ← response.data tampoco
El comentario en clientes.api.js:3 dice literalmente "Retorna siempre {ok, status, data}" — pero ningún sitio del código lo envuelve así. Es un contrato documentado pero no implementado.

🔴 BUG CRÍTICO 3 — Edit Tenant inoperante
tenants_manager.js:436-440 — el botón "Editar" muestra notificación "en desarrollo". Backend PATCH /api/public/v1/tenants/{id}/ ya existe.

4. ¿ES BUENO EL STACK ACTUAL? — RESPUESTA TÉCNICA
Tabulator + vanilla JS + HTMX es una elección válida para tu caso porque:
✅ Tu producto es CRUD-heavy con muchas tablas (asientos, facturas, clientes, productos…). Tabulator es mejor que la mayoría de grids de React para >10k filas y tiene paginación server-side de fábrica.
✅ Django + HTMX te da SSR + interactividad sin build step, lo cual reduce drásticamente costos de despliegue y CI/CD — clave si despliegas a clientes con infraestructura modesta.
✅ Tu modularización por feature (clientes/, contabilidad/, …) ya está bien estructurada.
✅ Sin node_modules, sin webpack/vite, sin “rotura por update de dependencia npm cada 3 meses”.

Pero el stack tiene problemas reales:
⚠️ Híbrido sin doctrina escrita — algunos módulos usan HTMX para cargar offcanvas (ej. clientes), otros hacen render local desde JSON (ej. tenants_manager). Sin convención clara, cada dev inventa.
⚠️ Sin testing E2E — los bugs descritos en §1 deberían haber sido detectados por un Playwright/Cypress de 30 líneas.
⚠️ Caché en cliente: nula — cada navegación entre tabs vuelve a llamar la API. Con 100 tenants y usuarios concurrentes, el backend va a sufrir.
⚠️ Búsqueda sin debounce verificable en tabulator.factory.js — cada tecla = un request.

6. PLAN DE ACCIÓN RECOMENDADO (priorizado)
Sprint 1 — DESBLOQUEAR EL CRUD (1 semana, 🔴 crítico)
Reescribir http.js para que retorne {ok, status, data} y exponga window.http como función (method, url, payload) además del objeto con métodos. Esto restablece la compatibilidad con todos los *.api.js existentes en una sola línea.

// pseudocódigo
const httpFn = async (method, url, payload) => { ... return {ok, status, data}; };
Object.assign(httpFn, { get, post, patch, put, delete: ... });
window.http = httpFn;
Cargar http.js en apps/tenant/core/templates/tenant/base.html (hoy solo está en consola pública).
Implementar Edit Tenant (tenants_manager.js:436) — backend ya existe.
Definir showError() global en ui-manager.js o eliminar referencias.
Smoke test E2E con Playwright — uno por módulo, 200 líneas total: login → crear → editar → eliminar.
Sprint 2 — CONSOLIDAR PATRONES (2 semanas)
Unificar offcanvas — un solo template parametrizable por modo crear|editar|detalle. Empezar por Clientes (referencia), replicar en Contabilidad, Proveedores.
Un solo data grid — extender tabulator.factory.js para cubrir el 100% de listados; eliminar restos de DataTables.
Estandarizar respuesta de error DRF vía un EXCEPTION_HANDLER único que retorne siempre {detail, errors: {field: [msg]}}.
Debounce búsqueda en tabulator.factory.js (300 ms).
Resolver primary_domain en ClientSerializer (ver auditoría previa).
Sprint 3 — DOCS & GOBIERNO (1 semana)
Crear FRONTEND.md — único doc vigente. 3 secciones: arquitectura (HTMX + Tabulator + módulos por feature), patrón offcanvas, contrato HTTP/error.
Mover documentacion/AUDITORIA_* y documentacion/ALINEACION_* históricos a documentacion/_archive/ con índice. Mantener vigentes solo API_FIRST.md, AJUSTES_BEST_PRACTICES.md, y los nuevos canónicos.
Versionado — adoptar una sola versión (v3.x) y borrar comentarios v2.25/v2.40/... confusos.
Sprint 4+ (a 6 meses, condicional) — MEJORAR UX
Solo si los problemas vuelven: introducir Alpine.js (8 KB) para reactividad declarativa en formularios. No reemplaza nada, se suma.
Caché de cliente con swr-pattern manual: dictionary Map por endpoint, TTL 30 s.
Tests de carga con generar_tenants_prueba --cantidad 50 y locust.
NO HACER (al menos 12 meses)
❌ Migrar a React/Vue SPA. La base de bugs no la causa el stack.
❌ Inertia.js. Es elegante pero te obliga a build step y reescribir templates.
❌ TypeScript ahora. Útil más adelante; primero arregla los bugs.

8. CONCLUSIÓN PERSONAL (sintetizada)
Tienes una buena arquitectura backend (django-tenants + DRF + JWT + Celery) y una dirección frontend sensata (Tabulator + módulos por feature + HTMX). Lo que está fallando es un cliente HTTP cuyo contrato se rompió a mitad de migración y una documentación que no refleja la realidad. Eso es deuda técnica resoluble en 4 semanas, no un problema de tecnología.

Migrar a React te haría perder 3-4 meses, te metería en CI/CD complejo, y los mismos bugs aparecerían por debajo si no arreglas la disciplina (tests E2E + un solo cliente HTTP + un solo patrón de offcanvas). La verdadera escalabilidad llega de la disciplina, no del framework.
